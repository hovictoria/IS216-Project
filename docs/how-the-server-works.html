Memory Go: how the server works

The Express API in IS216-Project/server, explained from the ground up. What a server is, what happens to one request from arrival to reply, and what each file is for.

In one sentence. The server is a program that sits listening on port 8000, and when the browser sends it a request, it checks who's asking, reads or writes the database on their behalf, and sends JSON back.

What a server actually is

Strip away the words and it's this: a Node program that never exits. It calls app.listen(8000), which tells the operating system "any network traffic to port 8000, hand it to me". Then it waits. Each time something arrives, Express wakes up, works out which of your functions should handle it, runs that function, sends the reply, and goes back to waiting.

That's the whole thing. A route is a function. Middleware is a function that runs before the route. The reply is JSON. There is no magic beyond "waits for messages, runs a function per message".

Express is a small library that does the boring parts: parsing the URL, matching it to your functions, reading headers, formatting the reply. You could do all that with Node's built-in http module, but it would be fifty lines per route instead of five.

How it compares to the lab server

Lab (q4 server.js)

  • Reads and writes equipment.json on disk
  • Four routes in one file
  • Anyone can call it; no idea who's asking
  • Whatever the browser sends, it saves

Memory Go (server/)

  • Reads and writes Supabase tables
  • One file per feature in routes/
  • Middleware verifies the user before every route
  • Server decides the rules (how much XP a game awards)

Same bones: express(), app.use(cors()), app.use(express.json()), app.get / app.post, app.listen. If you can read the lab's file you can read this one. The differences are what the routes do inside, and the doorman in front of them.

One request, start to finish

A page calls api.post('/progress/xp', { game: 'memory' }). Here's everything that happens on the server side.

0
browser
POST http://127.0.0.1:8000/api/progress/xp
Headers include Authorization: Bearer eyJ… (added by lib/api.js) and Content-Type: application/json. Body is {"game":"memory"}.
↓
1
app.listen
Node accepts the connection, hands it to Express
Express builds two objects: req (everything about the incoming request) and res (the reply you're building). They travel together through every function below.
↓
2
app.use(cors(...))
Is the browser origin allowed?
The browser is at localhost:5173, the server at 127.0.0.1:8000. Different origin, so the browser demands permission. cors adds the header that grants it, for CLIENT_ORIGIN only. Without this, the browser blocks the reply.
↓
3
app.use(express.json())
Parse the body: req.body = { game: 'memory' }
The body arrives as raw bytes. This turns JSON text into a JavaScript object so routes can read req.body.game.
↓
4
app.use('/api/progress', progressRoutes)
URL starts with /api/progress → hand off to routes/progress.js
Express checks the app.use lines top to bottom. The first prefix that matches wins. Inside the router, the remaining path is /xp.
↓
5
router.post('/xp', requireAuth, handler)
Method is POST and path is /xp → run requireAuth first
The functions listed after the path run left to right. requireAuth is middleware: it either replies and stops, or calls next() to continue.
↓
6
middleware/auth.js → supabase.auth.getUser(token)
"Whose token is this?" → user 123
The server never trusts an ID from the browser. It hands the token to Supabase and gets the user back. Bad or missing token: reply 401 here and stop. Good: req.user = user, next().
↓
7
routes/progress.js → the handler
amount = XP_FOR_GAME['memory'] → 50
The rule lives here. The browser said which game; the server looks up the value. An unknown game gets 400 and stops.
↓
8
supabase.from('progress')…eq('user_id', req.user.id)
Read the row, add 50, upsert it back
Uses the server's secret key, so RLS doesn't apply. That's why the .eq('user_id', req.user.id) is mandatory: it's the only thing keeping this user in their own row.
↓
9
res.json({ xp: 170, coins: 30 })
Reply sent. Status 200. Done.
res.json sets the content type, serialises the object, and ends the response. After this nothing else runs for this request.

server.js: the entry point

import 'dotenv/config'                  // read .env into process.env. Must be first.
import express from 'express'
import cors from 'cors'
import meRoutes from './routes/me.js'
import progressRoutes from './routes/progress.js'

const PORT = Number(process.env.PORT) || 8000
const CLIENT_ORIGIN = process.env.CLIENT_ORIGIN || 'http://localhost:5173'

const app = express()                   // the app: a list of functions to run per request

app.use(cors({ origin: CLIENT_ORIGIN })) // step 2 above
app.use(express.json())                 // step 3 above

app.use('/api/me', meRoutes)            // step 4: prefix → router file
app.use('/api/progress', progressRoutes)

app.get('/api/health', (req, res) => {  // no middleware: anyone can check the server is up
    res.json({ ok: true })
})

app.use('/api', (req, res) => {         // nothing above matched → 404
    res.status(404).json({ message: 'No such API route.' })
})

app.use((err, req, res, next) => {      // four arguments = error handler. catches thrown errors.
    console.error(err)
    res.status(500).json({ message: 'Something went wrong.' })
})

app.listen(PORT, '127.0.0.1', () => {   // start waiting. runs forever until Ctrl+C
    console.log(`Memory Go API running at http://127.0.0.1:${PORT}/api`)
})

Order matters. app.use lines run top to bottom for every request. cors and json must come before the routes or the routes won't have req.body. The 404 fallback must come after the routes or it would catch everything. The error handler must be last.

supabase.js: the server's database connection

import 'dotenv/config'
import { createClient } from '@supabase/supabase-js'

const url = process.env.SUPABASE_URL
const key = process.env.SUPABASE_SERVICE_ROLE_KEY

if (!url || !key) {
    console.error('Missing SUPABASE_URL or SUPABASE_SERVICE_ROLE_KEY. Copy .env.example to .env and fill it in.')
    process.exit(1)                     // quit now with a clear message, not later with a cryptic one
}

export const supabase = createClient(url, key, {
    auth: { persistSession: false, autoRefreshToken: false },  // a server has no logged-in user of its own
})

Same idea as the client's lib/supabase.js: one connection, exported, imported everywhere. Three differences: process.env instead of import.meta.env (Node, not Vite), the secret key instead of the publishable one, and session features switched off.

The secret key bypasses Row Level Security. Think of it as a master key to every user's flat. That's useful (the server can update anyone's score) and dangerous (it could read anyone's data by mistake). So every route carries the discipline the key doesn't: .eq('user_id', req.user.id) on every query.

middleware/auth.js: the doorman

import { supabase } from '../supabase.js'

export async function requireAuth(req, res, next) {
    const header = req.headers.authorization ?? ''                     // "Bearer eyJ…" or missing
    const token = header.startsWith('Bearer ') ? header.slice(7) : '' // strip the 7-char prefix

    if (!token) {
        return res.status(401).json({ message: 'Not signed in.' })    // reply and STOP (the return)
    }

    const { data, error } = await supabase.auth.getUser(token)         // ask Supabase whose token this is

    if (error || !data.user) {
        return res.status(401).json({ message: 'Session expired. Please sign in again.' })
    }

    req.user = data.user                                               // stick the verified user on the request
    next()                                                             // let the route run
}

A middleware is any function with the shape (req, res, next). The contract: either you send a reply (and don't call next), or you call next() (and don't send a reply). Never both. Whatever you attach to req is visible to everything that runs after you, which is how req.user reaches the route.

routes/progress.js: a feature router

import { Router } from 'express'
import { requireAuth } from '../middleware/auth.js'
import { supabase } from '../supabase.js'

const router = Router()                 // a mini app for one feature

const XP_FOR_GAME = { memory: 50, sequence: 40, pattern: 40, object: 30, missing: 30, oddoneout: 30 }

router.get('/', requireAuth, async (req, res) => { ... })      // GET  /api/progress
router.post('/xp', requireAuth, async (req, res) => { ... })   // POST /api/progress/xp

export default router

Router() groups the routes for one noun. The paths inside are relative to wherever server.js mounts it. One file per feature keeps server.js short and lets a teammate work on collection.js without touching anything else.

req and res: the two objects every function gets

req (the request, read it)

req.method'GET', 'POST'…
req.path'/xp' (relative to the mount)
req.headers.authorization'Bearer eyJ…'
req.bodythe parsed JSON (needs express.json())
req.params.idfrom a path like '/:id'
req.query.pagefrom '?page=2'
req.userours. set by requireAuth

res (the reply, build it)

res.json(obj)send JSON, status 200, done
res.status(404)set the code. chain .json after
res.status(201).json(obj)"created" + body
res.send('text')plain text (rare for an API)
return res…the return stops the function so nothing runs after the reply

You can only send one reply per request. Calling res.json twice throws "headers already sent". That's why every early exit is written return res.status(...).json(...): the return guarantees the rest of the function doesn't run and try to reply again.

Status codes we use

CodeMeaningWhen
200OKdefault for res.json
201Createdafter a successful insert
400Bad requestthe browser sent something invalid (unknown game, missing field)
401Unauthorisedno token or bad token. from the middleware
404Not foundno route matched
500Server errorSupabase failed, or an exception nobody caught

axios in the browser treats anything 400 or above as a thrown error, which is why page code wraps calls in try/catch.

The route pattern, every time

router.<method>('<path>', requireAuth, async (req, res) => {
    // 1. validate input from req.body / req.params. bad → return 400
    // 2. apply the rule (amounts, allowed values) on the SERVER
    // 3. query supabase, always .eq('user_id', req.user.id)
    // 4. error → return 500 with a plain sentence (never the raw error)
    // 5. res.json(data)
})

Four things never change: requireAuth in the middle, async because Supabase calls are awaited, req.user.id in the query, and return on every early reply.

Two things the browser never gets to decide: who it is (that's the token) and what things are worth (that's the route). The browser describes what happened. The server decides what it means.

The three security layers

The server sits in the middle. It's the only place with the secret key, and the only place the game rules live. That's the honest answer to "why have a server at all": without it, every rule would be in the browser where any player could edit it.

What changes on Vercel

Locally the server is a process that calls app.listen and runs forever. Vercel doesn't keep processes running. It runs your code as a serverless function: wakes it up per request, runs it, puts it to sleep. Four adjustments, all configuration:

  1. Export the app instead of listening. Keep app.listen for local dev but guard it, and add export default app so Vercel can call it per request.
  2. A separate Vercel project with root directory server/. The client gets its own project with root memorygo/. Both from the same repo.
  3. Env vars in the Vercel dashboard. The four values from .env, typed into the server project's settings. Nothing in git.
  4. CLIENT_ORIGIN becomes the client's Vercel URL, and the client's VITE_API_URL becomes the server's Vercel URL.

Everything in routes/ and middleware/ stays exactly as it is. The request flow in section 3 is identical; only "who starts the process" changes.

Glossary

porta numbered door on a machine. 8000 is ours, 5173 is Vite's. One program per port.
originscheme + host + port, e.g. http://localhost:5173. Browsers treat different origins as strangers; CORS is how a server says "this stranger is fine".
endpoint / routeone method + path the server answers, e.g. POST /api/progress/xp
middlewarea (req, res, next) function that runs before a route. Can reply early or pass along.
handlerthe (req, res) function that does a route's actual work
token / Bearer tokena signed string Supabase gave the browser at login. Proves identity without sending the password again. "Bearer" is just the header format.
service_role keySupabase's secret, all-access key. Server only.
publishable keySupabase's public key. Browser-safe because RLS limits what it can reach.
RLSRow Level Security: rules on a table about which rows each user may see or change
upsertinsert if the row doesn't exist, update if it does. Needs a unique column to match on.
JSONthe text format requests and replies use. express.json() parses it in, res.json() writes it out.
serverless functionhow Vercel runs the server: per request, not as a long-running process
