Memory Go: the login flow

What each file does, and what happens from the moment the app starts to the moment a user lands on the menu. Written from the steps we built together.

File map 1. App starts 2. Sign in 3. The guard 4. Sign up 5. Remembering 6. Sign out Vue cheatsheet JS cheatsheet
The one rule. Pages never talk to Supabase. They talk to the auth store. The store is the only file that imports the Supabase client. Everything else just asks the store "who is logged in?"

1. What happens when the app starts

The browser opens the site. Vite serves index.html, which loads main.js. From there:

client / page auth store Supabase router
1
main.js
createApp(App) and app.use(createPinia())
The app object exists but nothing is on screen yet. Pinia is switched on so stores work.
↓
2
main.js
const auth = useAuthStore()  →  auth.init().then(...)
Ask the store to find out whether someone is already logged in. The .then means "do the next part only after this finishes".
↓
3
stores/auth.js → init()
const { data } = await supabase.auth.getSession()
Supabase looks in the browser's local storage for a saved session from a previous visit.
↓
4
Supabase (in the browser)
Returns { session } or { session: null }
If a session exists and its token has expired, Supabase silently refreshes it first.
↓
5
stores/auth.js → init()
user.value = data.session?.user ?? null
Remember the user, or null. Then onAuthStateChange(...) subscribes so user stays correct for the rest of the app's life, including sign-out in another tab.
↓
6
main.js (inside the .then)
app.use(router)  →  app.mount('#app')
Only now does the router start. This ordering is why a refresh keeps you logged in: the guard never runs before the store knows the answer.
↓
7
router/index.js → beforeEach
Guard runs for the first URL
See section 3. It either lets the page through or redirects to /login or /menu.
↓
8
the page
landing.vue, login.vue, or menu.vue renders
AuthLayout draws the scene and card; the page fills the slot.
Why the wait matters. If app.use(router) ran before init() finished, the guard would see user === null for a split second on every refresh and bounce even a remembered user to the login page.
// src/main.js, the part that matters
const app = createApp(App)
app.use(createPinia())

const auth = useAuthStore()
auth.init().then(() => {        // wait for the session check
    app.use(router)             // now the guard has the right answer
    app.mount('#app')
})

2. What happens when you press Sign in

The user is on /login, types an email and password, and presses the button (or Enter).

1
login.vue → <form @submit.prevent="onSubmit">
The form fires submit. .prevent stops the page reload. onSubmit runs.
The form event catches the button, the Enter key, and the phone keyboard's Go key in one place.
↓
2
login.vue → onSubmit()
loading.value = true  ·  error.value = ''
The button greys out and reads "Signing in…". Any old error is cleared.
↓
3
login.vue → auth.signIn(email.value.trim(), password.value)
Hand the two values to the store and wait for its answer
The page doesn't know or care how sign-in works. It only knows the store returns null (good) or a sentence (bad).
↓
4
stores/auth.js → supabase.auth.signInWithPassword({ email, password })
Supabase checks the password and replies with { error } or no error
On success Supabase also saves the session in local storage and fires onAuthStateChange, so user is already set before the store even returns.
↓
success
store returns null
page: password.value = '', loading.value = false, then router.push('/menu'). The guard lets it through because isLoggedIn is now true.
failure
store returns a friendly sentence
page: error.value = message. The <p v-if="error"> appears above the button. Password box is cleared either way.
// login.vue
async function onSubmit() {
    loading.value = true
    error.value = ''

    const message = await auth.signIn(email.value.trim(), password.value)
    password.value = ''
    loading.value = false

    if (message) {
        error.value = message       // show it above the button
    } else {
        router.push('/menu')        // signed in
    }
}

// stores/auth.js
async function signIn(email, password) {
    const { error } = await supabase.auth.signInWithPassword({ email, password })
    if (!error) return null
    if (error.message === 'Email not confirmed') {
        return 'Please confirm your email first. Check your inbox for the link.'
    }
    return "That email or password doesn't match. Please try again."
}
Why the error is generic. If the message said "no account with that email", anyone could use the form to discover which emails are registered. "That email or password doesn't match" gives nothing away. The one exception is "Email not confirmed", because the user genuinely needs to know to check their inbox.

3. The guard: how pages get locked

Three pieces. Follow a logged-out user typing /menu into the address bar.

The route carries a label

{ path: "/menu", component: menu, meta: { requiresAuth: true } }

meta is a bag for your own notes about a route. Vue Router doesn't care what's in it. We put one flag there on every page that should sit behind the login. /, /login and /signup don't have it.

The guard runs before every page change

router.beforeEach((to) => {
    const auth = useAuthStore()

    // logged out and heading somewhere protected: sign in first
    if (to.meta.requiresAuth && !auth.isLoggedIn) {
        return '/login'
    }

    // already logged in: skip the landing, login and signup pages
    if ((to.path === '/' || to.path === '/login' || to.path === '/signup') && auth.isLoggedIn) {
        return '/menu'
    }
})

Vue Router calls this function before showing any page and hands it to, an object describing where the user wants to go. For our example to.meta.requiresAuth is true and isLoggedIn is false, so the function returns '/login'.

Returning a path means "go there instead"

That's the contract. Return nothing and the navigation continues as asked. Return a path and the original navigation is cancelled and the user goes there. The menu never renders; the login page does.

User isTypesGuard does
logged out/menuredirect to /login
logged out/ or /login or /signupnothing, page shows
logged in/menunothing, page shows
logged in/ or /login or /signupredirect to /menu
The guard is convenience, not security. It runs in the browser, so a user could switch it off in DevTools. It protects the experience. Protecting the data is the server middleware's job (every API request must carry a valid token) and Supabase's Row Level Security (a user only sees their own rows). Those come in steps 9 and 10.

4. Sign up

Same shape as sign in, with two differences: a local check before anything is sent, and a different store function.

1
signup.vue → onSubmit()
if (password.value !== confirm.value) { error.value = "Those passwords don't match."; return }
Checked in the browser first. No network call is made if they differ. The return stops the function right there.
↓
2
signup.vue → auth.signUp(email, password, name)
Store calls supabase.auth.signUp({ email, password, options: { data: { display_name } } })
The name is stored as user metadata on the Supabase user. You can see it in the dashboard under the user's "Raw user meta data".
↓
3
Supabase
Creates the user. If "Confirm email" is OFF, also signs them in straight away.
With "Confirm email" ON, the user exists but can't log in until they click the link in their inbox. For testing, turn it off in Authentication → Sign In / Providers → Email.
↓
4
signup.vue
null → router.push('/menu')  ·  message → error.value = message
Identical to login's last step.

5. How "remembering" works

After a successful sign-in, Supabase stores the session in the browser's local storage, under a key starting with sb-. On the next visit, init() finds it and the user is logged in without typing anything.

Stays logged in until…Does NOT log out on…
the user taps Sign outclosing the tab
site data for the app is clearedrestarting the browser
the session is revoked in the Supabase dashboardclearing the image cache

Remembering the email in the box after sign-out is a different thing. That's the browser's autofill, helped by autocomplete="email" on the input.

To force a logged-out state while testing before the sign-out button exists: DevTools → Application → Local Storage → delete the sb-… entry → refresh.

6. Sign out

The shortest flow of all. One button in the menu's sidebar, one store function.

1
menu.vue → <button @click="onSignOut">
onSignOut() runs
A plain button, not a link, because it does something before navigating.
↓
2
menu.vue → await auth.signOut()
Store calls supabase.auth.signOut() then sets user.value = null
Supabase deletes the sb-… entry from local storage and tells the server the session is over. The onAuthStateChange listener fires too, so even if the store forgot to set null, user would still clear.
↓
3
menu.vue → router.push('/')
Guard runs for /. isLoggedIn is now false, so nothing redirects. Landing page shows.
If the user now types /menu, the guard sends them to /login. Refresh keeps them logged out, because there's no session left for init() to find.
// menu.vue
async function onSignOut() {
    await auth.signOut()    // clears the session, user becomes null
    router.push('/')        // back to the landing page
}

// stores/auth.js
async function signOut() {
    await supabase.auth.signOut()
    user.value = null
}
Why await before the push. If you navigated first, the guard could run while the session still existed and bounce you straight back to /menu. Waiting for sign-out to finish means the guard sees the right answer.
